# 01 — Reverse-Engineering Cubbit DS3

**Status:** design input, evidence-based.
**Method:** black-box behavioural analysis from public material only — `cubbit.io`, `docs.cubbit.io`, and their published product/pricing pages. No proprietary source code, binaries, or internal protocols were used or decompiled. Where the public record is silent, this document says *INFERRED* and we specify our own equivalent.

**Correction to a common misconception:** "Cubbit" is not one system. It is two products built on one storage fabric, and they use *different* redundancy models. Getting this right is the single most important input to our design.

| | **DS3 Cloud** (managed) | **DS3 Composer** (software-defined, self-hosted) |
|---|---|---|
| Target | Ready-to-use cloud object storage, TB→PB | Operators running their own fabric, PB-scale, from ~200 TB |
| Fabric | Cubbit-operated swarm of third-party/partner data-centre nodes | Customer's own Swarm: their nodes, their sites |
| Redundancy model | **Flat** Reed–Solomon `n=20, n+k=60` (ratio 3.0×) | **Two-tier hierarchical** RS: `geo(n,k) × local(n,k)` (ratio 1.25×–3×, configurable) |
| Control plane | Cubbit-hosted Coordinator (SaaS) | Coordinator, either Cubbit-managed or self-hosted under licence |
| Who we clone | the *fabric semantics* | **the deployable product** ← our target |

Evidence: `docs.cubbit.io/getting-started/what-is-cubbit-ds3` (flat 20/60, ratio 3, recovery threshold `n + k/2`), `docs.cubbit.io/composer/swarms/what-is-a-swarm` (Nexus/Ring/Redundancy Class, two-tier ratio formula).

## 1. The published entity model

Cubbit's own glossary and Composer docs define a precise vocabulary. We adopt it almost verbatim, because a clone with a different vocabulary is not a clone.

### 1.1 Administrative hierarchy (control plane)

```
Operator ──owns──> Swarm ──contains──> Nexus ──contains──> Node ──contains──> Agent (1 per disk)
   │                                                                          
   └──creates──> Tenant ──contains──> Project ──contains──> Bucket ──contains──> Object
                                   └──> Users, Roles, Access Keys, Policies, Quotas
```

| Term | Definition (from Cubbit docs) | Our name |
|---|---|---|
| **Operator** | DS3 Composer user with admin privileges over the platform; creates Tenants and Swarms | `operator` |
| **Tenant** | Logically isolated domain with its own users, projects, policies, quotas, endpoint | `tenant` |
| **Project** | Container that owns buckets; has a root user, members, quotas, usage metrics | `project` |
| **Swarm** | Geo-distributed storage fabric = Nodes + Agents + Rings + Redundancy Classes + Nexuses | `swarm` |
| **Nexus** | Logical grouping of Nodes in one fault domain (DC / AZ / region). Geo-fencing unit. Equivalent to an AZ | `nexus` |
| **Node** | Physical or virtual machine contributing capacity; = one server | `node` |
| **Agent** | Containerised process managing **exactly one disk**; stores/serves shards, reports disk health | `agent` |
| **Ring** | Concrete instantiation of one Redundancy Class: an independent, bounded pool of Agents | `ring` |
| **Redundancy Class** | Policy `{geo_n, geo_k, local_n, local_k, aag}`; instantiated as one or more Rings | `redundancy_class` |
| **AAG** | Anti-Affinity Group = max Agents (disks) of a Ring on the same Node | `aag` |
| **Endpoint Gateway** | Per-tenant S3 hostname, e.g. `s3.<tenant>.cubbit.eu` | `endpoint` |

### 1.2 Storage hierarchy (data plane)

```
Object ──split into──> Chunk ──local RS──> Local Shard ──geo RS──> Geo Shard (stored on one Agent)
```

* **Chunk** — fixed-size portion of a file; *the minimum unit of redundancy*. Cubbit: "chunks are fixed-size portions and represent the minimum unit of redundancy within the Swarm."
* **Shard** — result of the redundancy process; the unit stored by one Agent.
* **File Key** — "an AES-256 key generated by the system to encrypt a file within the Cubbit network. Each file uploaded to DS3 is encrypted with a randomly generated File Key."

### 1.3 The components Cubbit names

| Cubbit component | Responsibility (their words) | Notes |
|---|---|---|
| **Coordinator** | "control plane… metadata-related operations, including shard placement, system health monitoring, authentication, and recovery workflows." "It does not store user data and is compatible with zero-knowledge encryption modes." | **Centralised.** Deployable managed (SaaS) or self-hosted. Multi-swarm, multi-tenant. |
| **S3 Gateway** | Access point exposing S3 API. Per tenant, public (`s3.<tenant>.cubbit.eu`) or private. | Node.js/Go; internal binary is called **`gods3`** (leaked in the KMS doc: "gods3 merges both files at startup"). Confirms Go. |
| **S3 Server** | Gateway sub-component: S3 API, request auth, **client-side encryption**, backend interaction | |
| **Offloader** | Gateway sub-component: "fragment and encrypt objects, apply redundancy policies, transfer fragments to/from Swarm nodes" | This is our *erasure-coding worker*. |
| **Cache** | Optional gateway cache for frequent reads / write bursts; shareable across a gateway pool via shared storage | |
| **Agent** | Container on each Node, one per disk: shards, upload/download, telemetry, disk-level policy | Deployed via generated Ansible recipes. |
| **Composer Hub** | `composer-hub.cubbit.eu` — agent announcement/bootstrap endpoint | Agents "announce" themselves with a secret + public key, land in `pending` status. |
| **DS3 Bridge** | Transparent S3→Cubbit migration: proxy-reads until migrated, deletes from source as it copies | `s3bridge.cubbit.eu`, `POST /bridges`. |
| **Console** | Web dashboard (Swarms, Nexuses, Nodes, RCs, Tenants, Projects, Buckets, Reports) | |
| **Composer CLI** | `cubbit` CLI (public on GitHub) | We need an equivalent. |
| **Gateway Operator** | Kubernetes operator installing gateways via `Gateway` CRD + ConfigMap `gods3-config` + Secret | |

## 2. The redundancy model — the heart of the system

### 2.1 Two-tier Reed–Solomon

A Redundancy Class is a pair of erasure codes applied in series:

```
   object chunk (plaintext)
        │  AES-256 encrypt + local RS(local_n, local_k)
        ▼
   local shards: local_n + local_k  per Nexus
        │  geo RS(geo_n, geo_k) across Nexuses
        ▼
   geo shards placed on Agents in geo_n + geo_k distinct Nexuses
```

* Readable while ≥ `geo_n` **Nexuses** are reachable, and each contributes ≥ `local_n` shards.
* Storage overhead = `ratio = ((geo_n+geo_k)/geo_n) × ((local_n+local_k)/local_n)`.
* Cubbit's documented examples:

| Topology | geo (n,k) | local (n,k) | aag | Ratio | Tolerates |
|---|---|---|---|---|---|
| Single site, 10 servers × 8 disks | 1,0 | 16,4 | 2 | **1.25×** | 2 whole servers / 4 disks |
| 3 sites, geo-redundant | 2,1 | 16,4 | 2 | **1.875×** | 1 whole site + 2 servers/site |
| Resilient multi-site | 3,2 | 4,2 | 1 | **2.5×** | 2 sites + 2 nodes per surviving site |
| Edge-optimised single site | 1,0 | 6,3 | 2 | **1.5×** | 3 nodes, all local |

### 2.2 Why hierarchy beats flat coding (and why DS3 Cloud uses flat 20/60)

Flat `20+40` costs 3.0× and tolerates 40 of 60 node losses. Cubbit's *cloud* swarm uses flat coding because its nodes are heterogeneous, unreliable, third-party devices (Cubbit Cells) — a single code with 60 wide stripe spreads risk maximally across an unreliable population.

Composer deployments have *structured* failure domains (racks, servers, sites). Hierarchical coding exploits that structure: `2+1 × 16+4` gives 1.875× overhead while surviving an entire site loss — flat `20+40` would need 3× and would still not guarantee site separation.

**We must support both**; they are two points on one configuration surface. Flat = `geo(1,0)` with local `(n,k)`. That is our key generalisation: **one code path, a RedundancyClass struct with a degenerate case.**

### 2.3 Recovery threshold (published)

From the DS3 Cloud doc: recovery is triggered when online shards fall to `n + k/2` (with 20/60: **50**). With hierarchical coding, the same rule applies *per tier*:

* per Nexus: online local shards < `local_n + local_k/2` → **local repair** (intra-Nexus, cheap).
* cluster-wide: reachable Nexuses < `geo_n + geo_k/2` → **geo repair** (cross-Nexus, expensive).

### 2.4 Repair without keys (a critical, clever property)

Cubbit's documented lazy-recovery step: a node fetches `n` shards, inverts Reed–Solomon "to obtain an encrypted chunk", redistributes — and "**it is not necessary to know the AES key used to encrypt the file to invert the redundancy process**."

This is only true if encryption happens **before** erasure coding (encrypt-then-code), and if the code is linear over the same field as the data bytes. Our design must preserve this: **the repairer is cryptographically blind.** A repair worker needs no key material whatsoever. This is what makes repair schedulable on untrusted nodes.

### 2.5 Placement heuristics (published)

The Coordinator selects peers on five axes (`what-is-cubbit-ds3`, "Heuristics on pool selection"):

1. **Uptime** — higher uptime ⇒ more likely selected.
2. **Geolocation** — balance latency (near) vs. blast-radius (far).
3. **Load average** — avoid concentrating related shards on one peer.
4. **Bandwidth** — balanced within a pool for uniform transfer speed.
5. **Peer history** — nodes switched off nightly get a low rank.

Plus: "runs machine learning algorithms to nullify the probability of losing files", and "spreads chunks as far as possible from each other while minimising network latency". Composer adds hard constraints: Nexus membership, AAG (max disks per server), Ring bounds, geo-fencing.

**What we cannot clone:** the exact ML model and its weights are proprietary and unpublished. We specify a deterministic, auditable, constraint-first scorer with the same five axes (§03). That is a faithful *behavioural* equivalent, not a bit-identical one. Stated plainly so nobody is surprised.

## 3. Security & encryption model as published

| Mode | Where the key lives | Who can read plaintext |
|---|---|---|
| `single-key` | one key for all tenants, gateway config | gateway + key holder |
| `local-multi-keys` | per-tenant key in gateway Secret file | gateway + key holder |
| `remote-multi-keys` | per-tenant key from Coordinator; **KMIP 1.4** KMS fallback for private tenants | gateway (transiently) + KMS |
| **zero-knowledge** (`zero_knowledge: true`) | key never leaves client; gateway only proxies ciphertext | client only |

Other published facts:

* Payload encryption is **AES-256**.
* Coordinator is "**cryptographically blind** — it only knows the files' location and their functional metadata."
* Gateway *polls the Coordinator* for per-tenant configs every `update_period` (default `1h`).
* KMIP requirement: one Managed Object of type `Secret Data` per tenant, name = tenant UUID.
* "All Gateways that serve the same tenant must share the same KMS configuration… A Gateway without the correct keys cannot decrypt objects uploaded by another Gateway."
* Per-tenant key **seed** is carried in the Coordinator response for non-zero-knowledge tenants (so the *seed* is in the control plane, and per-object keys are derived).

Consequence for our design: the Coordinator holds **tenant key seeds** but must never hold object keys or plaintext. Object keys are derived/random per object, wrapped, and stored with the object metadata in the control plane *only in wrapped form*.

## 4. S3 compatibility surface as published

Cubbit publishes an unusually precise compatibility table. Highlights (full matrix in `05-s3-api.md`):

* **Supported:** bucket CRUD, object CRUD, CopyObject, multipart (full), both list APIs + `ListObjectVersions`, ACLs (with restrictions), object lock (GOVERNANCE + COMPLIANCE + legal hold), tagging (object only, not at upload time), `NoncurrentVersionExpiration`-only lifecycle, ownership controls, SigV2 *and* SigV4.
* **Explicitly unsupported:** bucket policies (`PutBucketPolicy`=No), bucket tagging, CORS, website, replication, notifications, encryption config APIs, `SelectObjectContent`, `RestoreObject`, `GetObjectAttributes`, public access block.
* **Accepted but ignored:** all `x-amz-checksum-*` (not verified!), all SSE-C headers, conditional headers (`If-Match` etc. — "no 412"), `x-amz-tagging` at upload, `x-amz-mfa` enforcement, website-redirect, `x-amz-request-payer`.
* **Billing model:** minimum chargeable object size **256 KB**; bandwidth metered on downloads, reset monthly; object counts include zero-byte objects and delete markers.

Two deliberate deviations worth noting, and deciding on:

1. Cubbit **does not verify payload checksums**. Our clone *should* (correctness/durability), while still accepting the headers. We'll support them as an extension, defaulting on — documented as a deliberate improvement (`05-s3-api.md §9`).
2. Cubbit **does not implement conditional writes** ("targeted for early 2027"). We'll implement `If-Match`/`If-None-Match` because concurrent-writer safety is a durability feature, not a nice-to-have.

## 5. Deployment & operations facts

* **Per-disk sizing:** 1 CPU thread + 1 GB RAM **per Agent**, i.e. per disk. A 12-disk node ⇒ 12 threads, 12 GB minimum.
* **Node baseline:** 12+ bays, dual 10 GbE, 2× M.2 RAID1 boot, 12+ GB RAM.
* **Deployment mechanism:** the Console generates a **tar of Ansible recipes**; operator runs them; agents announce to Composer Hub with secret + public key; agent starts in `pending` and is activated on the dashboard.
* **Agent identity:** public key + secret; duplicate public key ⇒ `409 Conflict` (protects against the same disk being mounted to a different agent). Port mismatch ⇒ `400`. Wrong secret ⇒ `403`. `503` during maintenance.
* **Coordinator HA (self-hosted):** active-passive clustering; master-slave across one or two sites; stretch cluster to a third site; backup via DB dump (asynchronous, non-zero RPO). **This tells us the Coordinator is a *single-writer relational/embedded DB*, not a distributed consensus store.** (INFERRED, but strongly implied by "master-slave" + "DB dump".)
* **Gateway scaling:** stateless S3 servers + offloaders; optional shared cache on shared storage for a gateway pool.

## 6. What we are building — and what we are honestly not

**Building:** a Go implementation of a DS3-Composer-equivalent: Coordinator (control plane), Gateway (S3 + offloader), Agent (per-disk shard store), Console/API, CLI, Bridge, Operator — with two-tier Reed–Solomon, geo-fenced placement, self-healing repair, multi-tenant isolation, zero-knowledge mode, and a documented S3 compatibility matrix.

**Not building / not claiming:**
* Cubbit's exact P2P wire protocol, NAT traversal, or WebRTC signalling (not public).
* Their ML placement model and trained weights (not public).
* Their pricing, billing engine, or commercial machinery beyond usage counters.
* Any interoperability with the real Cubbit network. We are source- and protocol-incompatible with Cubbit; we are *behaviourally* compatible at the S3 API and *architecturally* equivalent.

**Name:** `FASS` — *Federated Adaptive Storage Service*. Binaries `fass-*`. No trademark collision, and the workspace is already `fass/`.
