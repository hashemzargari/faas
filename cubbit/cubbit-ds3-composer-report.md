# Cubbit DS3 Composer — Architecture Research Report

**Scope/method.** Enumerated `https://docs.cubbit.io/sitemap.xml` (60 URLs; 23 under `/composer/`), fetched every `/composer/*` page plus glossary, S3 API and Bridge guides, and the three marketing pages. The Composer doc tree is **narrower than assumed**: `composer/installation`, `composer/architecture`, `composer/nodes`, `composer/networking`, `composer/sizing`, `composer/operations`, `composer/upgrade`, `getting-started/{installation,requirements,architecture,nodes,networking,sizing,operations,upgrade}`, `composer/swarms/{nexus,nodes,redundancy-class}` all return **404**. Documented surface = `getting-started/` (2), `swarms/` (5), `coordinator/` (1), `gateway/` (4), `tenants/` (6), `dashboard/` (1). `llms.txt`/`llms-full.txt` also 404. Site is Docusaurus 3.10.2; sidebar is client-rendered, so the sitemap is the authoritative inventory. Many operational topics (node decommission, Coordinator upgrade, networking/ports, minimum cluster size) are simply **undocumented**.

## 1. Deployment model

DS3 Composer is a control-plane + data-plane split. Named components:

| Component | Role | Hosted by |
|---|---|---|
| **Coordinator** ("Composer/Controller", dashboard+API) | Control plane: auth/authz, shard placement, health monitoring, recovery workflows, node registration | **Cubbit (managed SaaS)** at `composer.cubbit.eu`, or **customer self-hosted "under license"** |
| **Swarm** | Logical grouping of nodes = the storage fabric; contains Nexuses, Nodes, Agents, Rings, Redundancy Classes | Customer (nodes), orchestrated by Coordinator |
| **Nexus** | Group of nodes in one fault domain — "Cubbit's equivalent to an availability zone" | Customer |
| **Node** | Physical or virtual server contributing capacity | Customer |
| **Agent** | "lightweight, containerized process" managing **a single disk**; holds shards, does upload/download, reports health, enforces redundancy | Customer |
| **Ring** | Concrete instantiation of one Redundancy Class over a set of Agents; unit of capacity | Customer |
| **DS3 Gateway** = **S3 server** (`gods3`) + **Offloader** processes + optional **Cache** | S3 API termination, client-side encryption, chunking, erasure coding, shard routing | **Public** gateway auto-created per tenant at `s3.<tenant>.cubbit.eu` (**Cubbit-managed**) or **private** (customer, on Kubernetes) |
| **Console** | `console.<tenant>.cubbit.eu` admin UI (Composer console for Operators; per-tenant DS3 Console) | Cubbit (or customer if self-hosted) |
| **Installer** | `installer.s3.cubbit.eu` → `gateway/installer.sh`, `k8s-setup.sh` (k3s bootstrap), Helm chart + **Kubernetes Operator** (`gateway-operator`) | Cubbit-supplied script, run by customer |
| **Ansible recipes** | Auto-generated tar bundle that configures storage nodes/agents ("Deploy nodes" bulk flow) | Generated by Composer, run by customer |
| **Composer CLI** (`cubbit`) | `gateway edit/describe`, SDP policies, "available on GitHub" | Customer |
| **Composer Hub** | Agent-facing announce endpoint (`composer-hub.cubbit.eu`) | Cubbit (or self-hosted) |
| **DS3 Bridge** | Experimental S3→Cubbit migration (proxied reads, delete-on-copy) | Gateway-side |
| **Cell** | Cubbit's own appliance/virtual node; legacy DS3-Cloud wording, absent from Composer flows | Cubbit |

Hierarchy: **Coordinator → Tenant(s) → Project(s)/Users → Swarm → Nexus → Node → Agent → Ring**, with **Redundancy Class** as policy and **Gateway** as the access edge. Auth: SAML 2.0, OpenID/OIDC, Google, Microsoft; roles Owner/Admin/Member/Read-only per Tenant and Swarm.

## 2. Node roles and sizing

**Roles:** **storage node** (runs Agents) and **gateway** (Kubernetes-deployed, stateless). There is **no documented "relay" role in Composer** — "relay" appears only in legacy DS3-Cloud copy ("a standalone device that acts as both a data storage unit and relay node"). No metadata/quorum node type exists; the Coordinator is that role.

**Sizing rules (docs, per disk):** "1 CPU thread … 1 GB of RAM" **per disk**, additive ("a machine with 12 storage disks will require at least 12 CPU threads and 12 GB of RAM"). Recommended 12×HDD node: "12+ cores (singlethreaded) / 6+ (multithreaded)", "12+ GB" RAM, 12+ hot-swap bays, "Dual 10 GbE (bonded/failover)", "2x M.2 in RAID1". Reference builds: Supermicro 1014S-ACR12N4H (EPYC 7313P 16c), SSG-521E-E1CR24H, SSG-640P-E1CR36H.

**Conflict to resolve:** the pricing FAQ states "1 vCore and 2GB of RAM for each HDD or SSD", gateway agent "4 vCores and 4GB" — 2 GB/disk, not the docs' 1 GB. Use the docs value but keep 2 GB as the safe budget.

**OS/hypervisor:** "A Cubbit node is a physical or virtual **Linux** machine"; VMware, KVM, Proxmox and clouds (EC2/Azure) are listed *for gateways*; gateways **require Kubernetes** ("A conformant cluster (on-prem, cloud, or edge)"), k3s via Cubbit's script, CNI Flannel (default) or Cilium. Agents are "containerized" and delivered via Ansible; **no Docker-Compose path is documented**.

**Minimum counts / capacity:** no explicit minimum cluster size is published. Derivable only from examples: a ring needs `local_n + local_k` Agents; the single-site example uses 10 servers × 8 disks = 80 disks with 16+4/AAG=2 producing 4 rings. Minimum commercial capacity: "Ideal for PB-scale, **starts from 200 TB**". Sites: 1 → multi-region; geo example uses 3 sites.

**Network:** per-node "Public IP address" and optional "Private IP address"; per-disk "disk prefix" and "designed port" (ports auto-incremented per disk). No port table, NAT/WebRTC guidance, or bandwidth formula is documented. Agents call the Coordinator over HTTPS (`composer-hub.cubbit.eu`, default `--coordinator-domain eu00wi.cubbit.services`).

## 3. Swarm / network topology

Agents **announce** themselves to the Coordinator over HTTP with a per-agent **secret** and **public key**; the Coordinator gates on `pending` status, port match, and secret match (documented error set: `400 Port mismatch`, `403 Secret not found`, `409 Agent with the same public key already exists`, `409 agent is not in pending status`, `503 under maintenance`). Data-plane traffic is **agent-to-agent P2P**: "Agents in the affected Ring establish peer-to-peer (P2P) connections with healthy Agents in the same Nexus."

The Coordinator holds **placement + health + policy metadata**, not payloads: "It does not store user data"; "The Coordinator is **cryptographically blind** — it only knows the files' location and their functional metadata." It is **centralised per deployment** (or shared): "A single instance can serve multiple Swarm deployments and multiple Tenants", and peer selection is scored on uptime, "Bandwidth", "Peer history" — legacy copy even claims "the Coordinator runs machine learning algorithms".

**Coordinator unreachable:** undocumented behaviour. Evidence: agents/troubleshooting treats hub DNS/timeout errors as "Ignore"; recovery threshold logic is Coordinator-driven (`n + k/2` online shards, "Lazy recovery strategy" below `d0`). **INFERRED:** the data plane (existing objects, gateway reads/writes across reachable agents) keeps working because placement is already materialised on agents and objects self-describe their shard set, while registration, re-placement, ring creation, and recovery stall — so a Go implementation should treat the Coordinator as a *soft* dependency with cached placement and local recovery triggers.

**Multi-tenancy:** Tenant = isolated domain with its own console, users, projects, quotas, policies; "Once storage is connected, it cannot be changed"; a tenant's storage may be vendor storage **or private Swarms**; agents may join multiple Rings "enabling multi-tenancy, hot/cold tiering, or isolated storage zones". Zero-knowledge tenants (`zero_knowledge: true`) keep key seeds out of the Coordinator, using local `tenant_keys` or KMIP 1.4 KMS.

## 4. Redundancy configuration

Fully customer-configurable per Redundancy Class, **two-tier Reed-Solomon**: `geo_n` (Nexuses needed), `geo_k` (extra Nexuses), `local_n` (Agents per Nexus needed), `local_k` (extra Agents per Nexus), `aag` (max Agents per node). Overhead `ratio = ((n_geo+k_geo)/n_geo) × ((n_local+k_local)/n_local)`.

Documented examples: (a) single site 16+4, AAG=2 → 20 shards, "Redundancy Factor of 1.25×", survives 2 server failures; (b) 5 Nexuses (3+2) with local 4+2, AAG=1 → survives 2 Nexuses or 2 nodes per surviving Nexus; (c) 3 sites, geo 2+1, local 16+4 → "combined redundancy factor is 1.875×", "for every 1.875 TB of raw storage, you can expect 1 TB of usable capacity"; (d) edge 1+0 / 6+3, AAG=2 (3 node failures, all data local). Legacy DS3 copy says "storing ratio of just 3". Targets: durability **99.999999999% (eleven nines)**, availability **99.95%**; pricing page additionally markets "11 nines, 15 nines". Rings are auto-created ("the maximum possible number of Rings"); an RC is bound to its Nexuses and must be recreated for another Nexus. **No replication-factor mode is documented** — erasure coding only (chunk = "minimum unit of redundancy", fixed size).

## 5. Operations

- **Add nodes:** bulk "Deploy nodes" wizard → recap → downloadable **Ansible tar**; "Scalability, by adding nodes incrementally without system downtime"; a new Ring is created when one nears capacity.
- **Drive failure:** per-disk Agent granularity; replace component + deploy new Agent; recovery "via the web interface or DS3 API"; agents P2P-reconstruct missing shards locally.
- **Site loss:** "A new Nexus is created by provisioning and registering replacement nodes… DS3 Gateways assist recovery by downloading enough data shards… Redundancy layers are inverted and re-encoded".
- **Rebalance:** "rebalance workloads over time without reconfiguring the whole system"; scale-out is ring-based rather than shard-reshuffle.
- **Upgrade:** Gateway re-runs the idempotent installer (`--version`, `--ingress` for TLS-only rotation, `--uninstall`); Coordinator self-hosted HA = active-passive, "Master-slave architecture across one or two sites", "Stretch clustering to a third site"; **Coordinator install guide is "not yet available publicly"**, and no upgrade page exists (404).
- **Monitoring/alerting:** Coordinator "continuously monitors the health of all nodes, Agents, and Nexuses"; resource metrics in the dashboard; per-resource notification thresholds ("Alert > Warning > Info") emailed to operators/owners; **usage reports** (`storage_bh` byte-hours, `egress_tb`, `ingress_tb`); 256 KB minimum billable object.
- **Backup/DR:** "Backup via DB dump for disaster recovery (asynchronous, non-zero RPO)"; gateway side: KMS misconfiguration "objects… become permanently unreadable".
- **Decommission:** only gateway `--uninstall` documented; node/agent decommission and data-drain are **undocumented (INFERRED: Agents are removed by deleting them in the UI so Ring membership shrinks and repair re-encodes).**

## 6. Licensing / commercials (public)

Three access models: **SaaS** (Cubbit Coordinator), **self-hosted** (Coordinator under license), **fully managed**. Signup is **invite-only**. Pricing: "Up to 3 TB: free tier access", "3-10 TB: personal-use rate (€4.99 / TB / month)", "10 TB+: discounted pricing… Get a custom quote"; DS3 Composer "starts from 200 TB"; 30-day 1 TB DS3 Cloud demo; no egress/deletion/API fees; per-project reserved free tier; white-label option; MSP/distributor fields (`code`, `external_id`) in reports.

## 8. Reimplementation notes / gaps

1. Model Nexus≈AZ, Node≈server, Agent≈**per-disk daemon** with own keypair+secret and an `announce` RPC (the only membership protocol the docs expose).
2. Placement is two-level (site → disk) with `aag` anti-affinity; RC is a 5-tuple from which Rings can be derived deterministically.
3. Undocumented (get from a trial/CLI): port numbers, NAT traversal, minimum node count, chunk size, metadata schema, Coordinator failover semantics, node drain.
